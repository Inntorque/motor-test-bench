# Inntorque 测功机统一接入协议 MBP/1

规范发布版本：1.1.0；线协议：1.0。规范、SDK 与上位机分别版本化。`schema.json` 是对象编号、CAN 标识符、字段类型及枚举的唯一来源；`contract.json` 定义单位、能力分级及时间要求。Windows 与 Ubuntu 使用相同编解码和控制逻辑。

## 接入方式与职责

新驱动板直接实现 MBP/1。已有驱动板可通过经过审查、随上位机一起签名发布的适配模块接入。现有 5014 保留原生 D0/02 适配；普通 MBP 驱动根据实际能力进入电流环或测功模式。适配模块必须回报真实能力、反馈来源及有效期；不可伪造厂家没有提供的测量量。

电机型号、额定参数、减速比和方向属于试验配置，不是驱动板通信身份。驱动板实际电流与保护边界优先于档案参数。外部传感器测得的输出轴扭矩与驱动器估算扭矩必须分别标识；后者不代替本机特性图的轴端实测值。

## 最低接入与能力分级

| 能力 | 必须实现 |
| --- | --- |
| 身份读取 | 16 字节唯一 UID、每次启动变化的 boot_id、硬件与固件版本、协议版本、模式及字段位图 |
| 电流环 | 模式位 1，Iq/Id/目标 Iq 反馈，完整电流边界，准备/启动/目标设置/停止，控制看门狗 |
| 测功模式 | 模式位 5 与 MAX_AVAILABLE_IQ 特性位；Iq/Id/当前参考、可用电流和限制原因；板端按已声明边界调节输出 |
| 力矩加载特性 | 以上一种控制模式，加电机轴转速、多圈位置、独立轴端扭矩传感器 |
| 温度 | 可选；一旦声明，必须提供有效温度及保护上限，失效会阻止或结束对应试验 |

位图为 `1 << 模式编号/字段编号`。电流边界包括 iq_min、iq_max、phase_protection_current、phase_run_limit_max。电流环实际可请求范围取 Iq 范围和两个保护边界的交集；不允许缺省为 10 A。不支持的模式拒绝启动，缺失反馈置空，不补零。

`MAX_AVAILABLE_IQ` 指板端在本次配置、母线、电流、温度及调制能力边界内提供可用输出，不等于已确认电机铭牌最大扭矩。达到软件设定/标定上限与实际堵转必须分开记录。

## CAN 与报文

CAN 2.0A、11 位标识符，DLC 按实际帧长度，STATUS/SAMPLE/STOP 为 8；节点 1–63，节点 0 保留。适配器波特率需与驱动板一致，不自动扫描或改写固件波特率。CAN ID = schema.frames 中的基址 + 节点号。STOP 的优先级高于心跳、状态、测量和请求。请求/应答采用经典 ISO-TP：SF 最多 7 字节；FF/CF 分包，FC block size 8、STmin 1 ms；普通 PDU 最大 1024 字节，诊断 PDU 最大 256 字节，分包超时 1000 ms。具体 FC、序号回绕规则须与标准 ISO-TP 及上位机测试向量一致。

PDU 头共 16 字节，所有多字节整数均小端：

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 4 | ASCII MTBP |
| 4、5 | 各 1 | 协议主、次版本 |
| 6 | 1 | 操作码 |
| 7 | 1 | flags，bit0=应答；其余定义以 schema 为准，保留位必须为 0 |
| 8 | 4 | request_id，由主机递增，与应答对应 |
| 12 | 2 | 正文长度 |
| 14 | 2 | 保留，必须 0 |

TLV 格式为 `对象 ID:u16 + 类型:u8 + 长度:u16 + 内容`。整数长度必须匹配类型，bool 仅 0/1，字符串 UTF-8，nested 内容仍为 TLV。拒绝越界、重复对象、错误类型、无效 UTF-8、保留位和不合法枚举；新增的未知对象在类型可解析时可忽略。不得通过修改旧对象含义实现升级。

应答正文前 4 字节：`result:u16 + stage:u8 + reserved:u8`，随后为结果对象。`ACCEPTED=0` 仅代表收到，`APPLIED=1` 代表已应用，`CONFIRMED=2` 为最终结果；PENDING 或前两个阶段不会完成主机请求。同一 request_id 最后必须返回 CONFIRMED 或明确错误。实际启动、停止、目标变更还要由新鲜 STATUS/SAMPLE 回读确认。动作应答超时后，上位机不自动重发动作。

## 控制会话与启动顺序

1. IDENTIFY 读取身份和能力，READ_STATE 获取新鲜状态。USB-CAN 打开不等于驱动连接完成。
2. 确认 READY、无故障、输出关闭；读取范围和所需反馈。协议主版本不一致只允许身份读取和 STOP。
3. CLAIM_CONTROL 正文为 `boot_id:u64, session_id:u64, run_generation:u32, command_seq:u32`。首次序号 1，session 随机生成，generation 比设备旧值递增。
4. PREPARE_RUN 带会话信封及运行配置 TLV。信封同上共 24 字节。设备逐项验证范围后回显实际配置并返回非零 prepared_id。配置未确认前不得开启输出。
5. START 引用 prepared_id。新鲜 STATUS 必须为 RUNNING、OUTPUT_ON，必要采样有效；主机才显示启动成功。
6. SET_TARGET 更新目标；当前目标 Iq 必须新鲜回读确认。Iq 是有符号 mA 峰值；主机固定 direction=+1，并以 Iq 符号表达当前控制坐标系下的方向，板端不可再次反向取负。
7. STOP 不依赖控制会话，不受故障或过期 session 阻止。

所有写操作检查 boot/session/generation/sequence。旧启动命令不能在一次 STOP 后恢复输出。精确重复请求按当前启动周期的去重缓存返回原结果，不重复执行动作；缓存深度及最大包长见 schema。CLEAR_FAULT 不自动启动电机，故障仍存在时应拒绝或明确报告。

## 状态、停止与时序

STOP 为原始 8 字节 CAN 帧：ASCII `STOP` + `stop_id:u32`。板端立即撤销控制输出，更新状态；STATUS.last_stop_id 必须对应本次 STOP，OUTPUT_ON 为 0，状态为 DISABLED 或 FAULT。停止命令已发送与输出关闭已确认是两种状态。

STATUS：`state:u8, mode:u8, flags:u16, last_stop_id:u32`。推荐每 100 ms 发布。主机控制心跳每 250 ms；驱动声明自身看门狗（本接入档案要求大于 250 ms 且不大于 1000 ms），租约失效时在 MCU 内关闭输出。设备心跳不能替代新鲜 STATUS 或必要的实际反馈。诊断数据刷新频率单独管理，不能把可选诊断未刷新当作全部控制反馈过期。

主机当前状态/测量有效窗口为 1.5 s；启动与停止实际确认超时 2 s；普通请求应答超时 3 s。设备复位必须更换 boot_id，使旧会话和旧采样失效。CAN 断开与电源断开是独立状态，不得以通信断开推断电机已关闭。

## 同组采样与单位

SAMPLE 帧：`sample_seq:u16, field_id:u8, flags:u8, raw_value:u32`。flags bit0=有效，其他保留/扩展位依 schema，未定义位为 0。同一采样组的所有字段使用相同 sample_seq；最后发 field_id=254、raw_value=本组字段位图。仅收齐并核对位图后提交整组；0/1 时间字段必须成对存在，6/7 位置字段必须成对存在。重复字段、重复提交、丢帧组不参与有效采样。

Iq、Id、相电流为 mA 峰值；母线电流为 mA 直流量；电压 mV；转速为电机轴 0.001 rpm；温度 0.001°C；位置为有符号 int64 微转（低 32 位字段 6，高 32 位字段 7）；设备时间为自启动起的 u64 微秒（字段 0/1）。量纲和机械位置必须按 contract.json 对齐。减速箱输出轴转速根据明确的试验减速比换算，不能把传感器端与电机轴单位混用。

设备时间、主机接收时间、整理时间分别保留。不把异步电源读数冒充同一 MCU 采样；特性图只采用后台接受的加载点，原始记录持续保存。

## SDK、参考接入与验收

将 `sdk/device/mb_sdk.c` 加入固件并添加该目录为头文件路径，或通过 CMake 的 `add_subdirectory` 链接 `motor_bench_sdk`。C11 设备栈包含双路 ISO-TP、能力查询、会话、命令去重、STOP、心跳看门狗和采样。独立的 `sdk/mbp_wire.c/.h` 提供 C99 报文编解码。

1. 在 `mb_port` 中绑定非阻塞 CAN 发送、微秒时钟、启动标识、能力描述、状态与采样回读、准备、启动、目标设置和输出关闭。参考 `examples/simulator.c` 中的实现。产品端为每次上电提供新的 boot_id，按实际硬件填写能力和限制。
2. 用 `mb_config{MB_SDK_API, 节点号, 看门狗毫秒数}` 初始化。CAN 接收中断将对应的 8 字节标准数据帧交给 `mb_sdk_on_can_rx_isr`。主循环按单调微秒时间频繁调用 `mb_sdk_poll`。驱动本身负责过温、过流及输出保护。
3. 准备及目标回调同步返回结果。启动回调可返回 MB_OK 或 MB_PENDING，协议栈随后读取实际状态，确认 RUNNING、指定模式及输出开启后才发最终 CONFIRMED。故障或超时会请求关断。STOP 回读包含 last_stop_id。
4. 用 `cmake -S sdk/device -B build` 和 `cmake --build build` 构建静态库。上位机仓库的 `npm run protocol:check` 将当前 SDK 编译为虚拟设备，经真实主机协议栈验证电流环和测功模式。

`examples/driver_descriptor.json` 是第三方电流环驱动的能力示例。`tests/protocol-integration.test.js` 使用非 5014 虚拟驱动验证标准电流环、测功、范围拒绝、真实回读和停止。真实硬件验收还需执行接入清单，软件模拟通过不代表任何未测试硬件已经兼容。

执行 `npm run protocol:check` 检查生成文件与 C/TypeScript 标准报文一致性；执行 `node --test tests/protocol-integration.test.js` 检查主机接入。新增能力先更新协议规范及测试，兼容性破坏必须增加主版本。上位机在线更新不自动刷写驱动板固件。
