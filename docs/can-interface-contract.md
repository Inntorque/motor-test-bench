# CAN 接口约定 v1

日期：2026-10-08。用于固定本项目的开发范围，尚未实现或完成实机验收。用户已确认适配器为鹿小班 **LC_CANABLE_V2.1**，允许根据方案修改固件。

## 1. 本轮确定的范围

| 层级 | 项目约定 | 状态 |
| --- | --- | --- |
| 板卡 | LC_CANABLE_V2.1 | 用户已确认 |
| 电脑连接 | USB CDC 虚拟串口，由网页 Web Serial 访问 | 采用的实现方向；需核对实机固件 |
| 适配器协议 | CANable SLCAN ASCII，CR 分帧 | 固定为网页适配器层基础 |
| 首轮 CAN 帧 | 经典 CAN 数据帧，11 位或 29 位 ID，0–8 字节 | 固定为首轮实现/验收范围 |
| 首轮速率选项 | 125、250、500、1000 kbit/s | 计划支持；实际值随驱动板配置，未设默认总线速率 |
| RTR、CAN FD、BRS | 独立扩展能力 | 当前不作为首轮已支持功能；若现有驱动需要，先扩展验收范围 |
| 电机应用协议 | 单独的驱动板协议配置与编解码模块 | 尚未取得本次驱动板协议；不从其他电机复制报文 |

传输链路为：网页 → Web Serial → USB CDC/SLCAN → CAN → 驱动板。SLCAN 负责把 CAN 帧传过 USB；帧里的“使能、速度、故障”等含义由驱动板协议定义。适配器固件可修改，不代表更改了驱动板能理解的命令。

此处的首轮速率选项是软件支持范围，不代表试验台已经采用这些速率。只有与驱动板匹配的配置才能用于联调；不自动扫速率发送电机命令。

## 2. USB 与流格式

网页通过明确的连接按钮请求串口授权。默认打开参数定为 `115200, 8N1, flowControl=none`；CAN 速率用 SLCAN 命令另行配置。

本地参考固件忽略 USB CDC 的 `SET_LINE_CODING`，`GET_LINE_CODING` 返回 115200/8N1；这个数值不能当作真实 UART 吞吐上限或 CAN 位速率。本地 USB CDC 实现（工作区参考：`engineering/realman/firmware/work/canable2-whj/src/usbd_cdc_if.c`）、[Web Serial 文档](https://developer.chrome.com/docs/capabilities/serial)。

- 命令及帧使用 ASCII，每条以 CR (`0x0D`) 结束。
- 一次串口读取可能包含半条、一条或多条记录，解析器必须跨读取保留缓冲。
- 经典帧按下表严格校验 ID、长度和十六进制数据，不把版本/诊断字符串当作 CAN 数据。
- 发出十六进制数字采用大写；接收数据数字可接受大小写，首字符 `t/T` 必须区分。
- v1 不解析未协商的时间戳尾部；未知扩展作为诊断记录，不能静默当成有效帧。
- 单条记录缓冲建议上限 512 字节；超限后丢弃到下一个 CR 并报告解析错误，避免后半段被解释为一条新命令。

## 3. 经典 CAN 数据帧

| 类型 | SLCAN 格式 | 校验 |
| --- | --- | --- |
| 标准帧 | `tIIILDD...\r` | ID 为 3 个十六进制字符，范围 `0x000–0x7FF` |
| 扩展帧 | `TIIIIIIIILDD...\r` | ID 为 8 个十六进制字符，范围 `0x00000000–0x1FFFFFFF` |
| 长度 | `L` | 单字符，取 `0–8` |
| 数据 | `DD...` | 恰好 `2×L` 个十六进制字符，不为 CAN DLC 静默补零 |

上、下行 CAN 数据帧使用同样布局。SLCAN 中的 ID 以十六进制文本表达；CAN 载荷中的多字节字节序由电机协议规定，不能从 SLCAN 推导。

离线编解码示例（不代表电机控制命令，不发送到实物）：

```text
标准 ID 0x123，数据 01 02：t12320102\r
扩展 ID 0x001ABCDE，数据 AA BB CC：T001ABCDE3AABBCC\r
标准 ID 0x001，零字节数据：t0010\r
```

首轮界面不生成 RTR 帧，也不把 FD 帧降级成经典帧。遇到这些帧时明确提示当前配置不支持；扩展支持需单独增加帧类型、长度映射和验证。

布局来自 [CANable SLCAN 固件](https://github.com/normaldotcom/canable2-fw)。上游支持更多命令及非标准 FD 扩展，不表示本项目首轮对这些能力全部做出兼容承诺。

## 4. 配置与结果反馈

| 命令 | 用途 | 项目处理 |
| --- | --- | --- |
| `V\r` | 固件版本 | 用于识别经过验证的固件版本，不能仅凭包含 CANable 字样判定兼容 |
| `C\r` | 关闭 CAN 通道 | 配置前关闭；不能等同于电机停止 |
| `S4/S5/S6/S8\r` | 125/250/500/1000 kbit/s | 仅在通道关闭时配置 |
| `O\r` | 打开 CAN 通道 | 打开后仍需匹配的驱动板反馈，才能显示电机在线 |
| `M0/M1\r` | 正常/静默模式 | CANable 扩展；按已验证固件能力使用 |
| `A0/A1\r` | 关闭/开启自动重传 | CANable 扩展；策略写入设备配置，不能静默继承未知值 |
| `E\r` | 查询错误 | 响应是固件相关诊断文本，按版本解析 |

串口打开、适配器配置和电机在线分别显示。串口写入成功只表示主机提交了字节；CAN 控制器发送结果是第二层状态；驱动板应答与实际反馈是第三层状态。三者不能合并成“操作成功”。

上游及现有 WHJ 参考固件不为普通命令返回通用 ACK/NACK，不能等待每条命令后必有 CR 或 BEL。固件诊断扩展 `Q/J/P` 也带项目定制，不作为通用 SLCAN 必需命令。[上游说明](https://github.com/normaldotcom/canable2-fw)、本地命令回传实现（工作区参考：`engineering/realman/firmware/work/canable2-whj/src/usbd_cdc_if.c`）。

正式台架固件应提供可验证的配置状态、错误和队列统计。若增加确认、能力查询或时间戳扩展，应先定义版本化的消息格式与协商方式，再同时实现固件和网页；本 v1 不虚构现有固件已具备这些扩展。未知固件不自动进入电机控制流程。

## 5. 固件复用边界

现有鹿小班实验固件（工作区参考：`engineering/realman/firmware/README.md`） 可参考板级映射、USB CDC 和 SLCAN 收发；其中的 WHJ 时序、版本名称、诊断输出与初始化流程需要独立处理。该工程曾记录位错误和 ACK 错误，不能把旧二进制作为本项目已验证固件。

本项目固件交付时应固定源码版本、构建参数、板级配置和二进制校验值，并记录通过实机验证的速率。当前只是固定支持板型，不推断电脑上此刻连接了哪块实物、运行哪版固件。

网关保持通用帧传输职责。上电不发送电机控制报文；关闭或 USB 会话结束时处理旧队列，重连不重放旧目标。通信丢失时电机如何处理必须由驱动板协议和控制实现明确；关闭 CAN 或停止发帧不能单独证明电机已经停止。

## 6. 电机协议的下一步

本轮在工程里找到 WHJ、达妙及外购驱动相关实现，尚未找到能确认属于本次自家驱动板的协议定义。因此没有分配新的电机 CAN ID、编造使能命令或修改驱动板协议。

已有协议时，只需补齐一份明确的设备配置与编解码定义：

- 协议名称/版本、驱动板固件、经典 CAN 或 FD、总线速率、节点与 ID 分配。
- 工作模式、使能/停止、设定值、参数读取及对应命令应答。
- 各字段的字节序、类型、比例、单位、有效范围和缺失值定义。
- 电机侧与输出侧的转速/位置/扭矩语义，减速比和方向约定。
- 反馈周期、状态字、故障、通信超时与重新连接后的状态。

若驱动板协议尚未固定且由我们定义，建议先用经典 CAN 数据帧，11 位 ID 作为简洁起点，总线速率再结合驱动和布线确认。使能、停机、模式切换和命令确认须有明确状态机；实时电流/速度环由驱动板执行。未收到该方向确认前，不把新报文表写成现有设备事实。

## 7. 后续实现验收

1. 离线编解码：标准/扩展、0/8 字节边界、非法 ID/DLC/字符、分包/粘包、超长输入与未知消息。
2. 固件识别：已知版本、未知版本、配置失败与无应答分别反馈，不显示虚假的就绪状态。
3. 适配器联调：本次板型上的已选速率、收发、错误/溢出、关闭和拔插恢复。
4. 驱动板联调：已知只读响应、数值单位和控制应答，之后才验证具体运动行为。
5. 页面与记录：CAN 与 RS485 独立状态、同一电脑时间基准、断线缺口与操作事件；不声称硬件同步采样。
